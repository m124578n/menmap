# menmap Roadmap

現況與待辦。階段代號沿用 `architecture.md`(P0 前端、P1 詳情 API、P2 部署、P3 收尾)。

## 現況(2026-09)

- ✅ 採集 pipeline(家裡):static / playwright 雙後端,617 家 seed(雙北、已過濾台式雜訊)
- ✅ P0 前端:MapLibre 地圖 + 篩選 + 詳情面板,和風設計,深色模式
- ✅ P1 詳情 API:Worker(Hono)+ D1,`/api/shop/:ftid` 回營業時間/評論/照片/趨勢
- 🔜 資料覆蓋:D1 目前約 30 家有完整詳情;static 全抽(617)進行中,補齊營業狀態與基本資料

## 待辦

### 拉麵種類分類(雞白湯/豚骨/醬油/家系…)— 延後用 LLM 處理

**決策**:等評論資料齊了,用 **LLM 一次性分類**(名稱 + 評論文字 → 主湯頭標籤,多標籤)。

**為什麼不用其他方法**(2026-09 實測,免得之後重查):

- **名稱關鍵字**:只有 **11%(66/617)** 能從店名分出來——多數店叫「麵屋武藏」「凪 Nagi」
  「一風堂」,不把湯頭寫在名字。精準但覆蓋太低。
- **Google 編輯描述(description 欄位)**:❌ 走不通。實測 place/search 回應的描述大多是
  None,有值也只是「供應拉麵和日式料理的當代餐廳」「早午餐」「可帶狗入住」這種籠統標籤,
  **從不提湯頭**。不值得為它加採集欄位。
- **評論關鍵字(naive)**:有評論的店 **100%** 命中,但**過度貼標**——一家店常被貼 5~6 種
  (評論會提到各種湯頭、客人比較),精準度差。
- ✅ **評論 + LLM**:評論提供原料(豚骨/雞白湯/湯頭…實測神山評論明確寫「魚介和豚骨雙湯頭」),
  LLM 判斷「這家主打什麼」並濾掉比較性雜訊,精準度最高。

**前置條件**:先讓 Playwright 把評論抓到足夠覆蓋(目前僅 ~30 家有評論;要靠每日排程或分批
補到大部分 617 家)。

**實作草案**:
1. 一次性腳本 `scripts/classify_types.py`:讀 D1/ramen.db 的 shop.name + review.text,
   對每家店呼叫 Claude(單次 batch,便宜),輸出多標籤 categories。
2. 分類結果寫回 shop 表(新增 `categories` 欄位,JSON 陣列)。
3. `export_web_data.py` 把 categories 帶進 `shops.json`。
4. 前端加「類型」篩選 chip(多選,多標籤;一家店可同時是豚骨+家系)。
5. 之後新店或評論更新時再增量重跑。

**備選**:LLM 之前想先有東西,可先上「名稱關鍵字 + 知名連鎖對照表(一風堂/屯京/一蘭→豚骨、
一幻→蝦、Nagi→煮干…)」的精準子集,標好明確的、其餘「未分類」,LLM 版上線後取代。

### P2 — 部署上 Cloudflare(家裡 publish 自動化)

- `wrangler d1 create menmap` → 遠端 D1;schema 上遠端
- 家裡 `run_daily.ps1` 加 publish 步驟:`shops.json` → R2、變動列 → ingest Worker 寫遠端 D1、
  新店封面照 → R2(scoped token,全 outbound)
- 前端 Pages、API Workers 部署

### P3 — 收尾

- 地圖底圖換自架 **Protomaps pmtiles**(存 R2,去除 CARTO 外部依賴)
- **照片快取進 R2**:googleusercontent 熱連結會間歇失效(目前破圖自動隱藏、顯示時放大解析度),
  改成採集時下載封面/評論照存 R2,穩定且可控
- 評分/營業狀態的歷史趨勢視覺化強化

### P4 — 使用者功能(登入 / 最愛 / 造訪紀錄 / 等候回報)

把 app 從唯讀變成有帳號、有寫入的產品。需要認證、per-user 資料、群眾共享資料,
以及寫入端的濫用防護。全部仍可 Cloudflare-native、零成本。

**存取原則:不登入也能用,登入才解鎖個人/寫入功能。**
- **免登入(公開)**:看地圖、篩選、拉麵骰子、店家詳情、營業時間、評論、菜單照——
  全部照用。這是現在的唯讀 MVP,不會因為加了登入而擋人。
- **需登入**:我的最愛、麵史(造訪紀錄/留言)、排隊/等候回報——凡是「寫入」或「屬於你個人」
  的功能才要登入。
- UI:未登入時這些功能顯示登入引導(而非隱藏),點下去才提示登入。
  這也正是 P0 選「唯讀優先 + hybrid」架構的好處:公開內容走靜態/快取,個人功能才打帶驗證的 D1。

#### 4.0 認證(前置,其餘功能都依賴)

- **做法**:Worker 自己處理 OAuth(建議 **LINE Login**——台灣用戶普及;或 Google),
  callback 驗證後簽發 **HttpOnly 簽章 session cookie(JWT,Worker secret 簽)**,
  不靠外部 auth 服務,維持零成本。
- D1 `user` 表:`id, provider, provider_id, display_name, avatar_url, created_at`。
- 所有寫入端點驗 session;加基本 rate limit 與濫用防護。
- **備選**:Clerk / Supabase Auth(程式少但外部依賴、可能超出免費圈)——與零成本原則衝突,
  預設自建。
- **待定**:登入提供者(LINE / Google / 兩者)。

#### 4.1 我的最愛

- D1 `favorite(user_id, ftid, created_at)`。
- API:`POST/DELETE /api/favorites/:ftid`、`GET /api/favorites`。
- 前端:卡片/詳情的愛心 toggle;「我的最愛」篩選或分頁。

#### 4.2 造訪紀錄 → 歷史回顧(暫名「麵史」)

- D1 `visit(id, user_id, ftid, visited_at, my_rating?, note?)`——「我某天在這吃過」+
  **每筆附註/留言**(例:「這家的唐揚雞特好吃」「湯頭偏鹹」「記得加辣」)。
- 附註是個人的(per-user),屬於自己的紀錄;之後可選擇性做成可分享。
- API:`POST /api/visits`、`GET /api/visits`(本人時間軸)。
- 前端:詳情「記錄造訪」(可寫附註 + 給自己的評分);
  **「麵史」頁**——個人吃麵歷史:時間軸 + 造訪過的店標在地圖 + 自己的留言 +
  統計(吃過幾家、最常去的區、每月次數、口袋清單完成度)。
- 命名:暫定 **麵史**(麵+歷史 諧音);備選:拉麵護照 / 麵歷 / 食麵記。

#### 4.3 排隊人數 / 等候時間回報(群眾共享)

- D1 `wait_report(id, ftid, user_id, queue_count, est_wait_min, reported_at)`。
- **目前估計**:取近 30~60 分鐘的回報,依新鮮度加權;沒有近期回報就不顯示(過時資料無用)。
- 前端:詳情「回報排隊」(人數 / 預估分鐘);卡片/詳情顯示「目前約 15 分 · 5 分前回報」。
- **難點**:冷啟動稀疏(多數店沒人回報)、可信度/濫用、時效性。
- **關鍵補強**:Google 地圖有「**目前繁忙程度 / 熱門時段(popular times / live busyness)**」,
  採集時**很可能抓得到**(place 回應內),可當作**零使用者也有的基準**,群眾回報疊上去校正。
  → 先驗證採集端能否穩定拿到 popular times;能的話它就是等候功能的底層資料,回報是加值。
- 需登入才能回報(可課責、減少灌水)。

#### 資料架構影響

- D1 從「只有家裡 publish 寫」變成「家裡 publish + 使用者寫」;user 表與 shop/snapshot 併存。
- 讀寫分離仍成立:地圖/列表走 `shops.json`(靜態、快),使用者資料與等候估計走 Worker + D1。
- 這正是 P0 選 hybrid 架構的原因,現在把 D1 的寫入面補上。

### 地區擴充(雙北 → 台中 → 高雄 → 全台 → 日本)

分階段擴大涵蓋範圍。採集端與前端大致 region-agnostic,主要工作是關鍵字/地區設定與**規模**。

**階段**:
1. 雙北(現況)
2. 台中、高雄(各大都會)
3. 全台
4. 日本(全台穩定後)

**每階段要做的**:
- seed 關鍵字擴充(各縣市/行政區,如 `拉麵 台中西區`);把 `ramen/seed.py` 的
  `_in_twin_cities` 地區守門改成**可設定的地區清單**(config-driven,不再寫死雙北)。
- 過濾規則沿用(台式雜訊過濾對全台同樣適用;日本則幾乎沒有此問題)。

**關鍵架構轉折(規模):`shops.json` → D1**
- 現在 617 家整包成一顆 `shops.json` 前端載入、client 端篩選——這在數千家內都還行
  (幾 MB)。這是**現階段的過渡做法**。
- **終態:店家清單也由 D1 出**。`shops.json` 會被 D1 取代——前端只向 Worker 要
  「目前地圖範圍內」的店(D1 空間查詢 + bbox 索引;或分區塊的靜態檔快取熱門範圍)。
  詳情(P1)本來就走 D1,清單併過去後資料來源統一。
- 觸發點:到全台(上萬家)/ 日本(數萬~數十萬家),單一 JSON 過大、初次載入慢時。
  → 越早把前端的資料存取抽象成「依範圍取店」介面越好,之後把後面從 shops.json
  換成 `GET /api/shops?bbox=…` 就不用動 UI。
- 採集量同步暴增:住宅 IP 的請求量與被擋風險上升,需**分區、分日排程**慢慢鋪,
  而非一次抓完;每日排程改成輪流跑不同地區。
- 分類(P4 LLM 種類)、等候(popular times)等功能對日本資料同樣適用,且日本 Google
  資料通常更完整。

### 店址沿革(同一位置的店家更替紀錄)

同一地點的拉麵店換人時,保留紀錄:可看「這個位置之前是哪間店、從幾年幾月到幾年幾月」。

**核心問題**:Google 在店家更替時給**新的 place_id/ftid**,且不可靠地保留前一手資訊。
所以「位置」不是穩定鍵,需要自己把不同 ftid 綁到同一實體地點。

**做法**:
- 加「位置 id」:座標 **geohash**(精度約 10~30m)或正規化地址,把鄰近/同址的不同 ftid
  歸為同一地點。`shop` 加 `location_id`;或另建 `location(id, lat, lng, address_norm)`。
- 生命週期:`shop` 的 `first_seen` / `last_seen` 已有;快照偵測到 `CLOSED_PERMANENTLY`
  時記 `closed_at`(每日 diff 已經在標記永久停業,直接接上)。
- 更替偵測:seed 更新時,若某 `location_id` 出現**新 ftid**、而舊 ftid 已永久停業/消失,
  記為一次更替。
- 呈現:單店詳情或位置頁顯示該地點的**時間軸**——
  「拉麵店 A(2026-09 ~ 2027-03,已停業)→ 拉麵店 B(2027-05 ~ 至今)」。

**誠實的限制**:
- 只能**從爬蟲開始(2026-09)往後累積**,無法回填爬蟲開始前的歷史(Google 不可靠地提供
  前一手)。→ 價值隨時間累積,越早開始記越有料;現在就把 `location_id` + `closed_at`
  這些欄位補上,資料才會從今天開始沉澱。
- 座標會有誤差:新舊 listing 的 lat/lng 可能略不同,geohash 需適當精度 + 地址輔助比對,
  避免把隔壁店誤綁成同一位置。

**先做的最小步**(低成本、先開始沉澱資料):採集/入庫時就寫入 `location_id`(geohash)與
永久停業時的 `closed_at`;沿革的 UI 之後再做。

### 粉專(FB/IG)— 記錄連結,不爬內容

需求:有些店把公休/臨時營業時間公布在 FB/IG 粉專,而非 Google。

**現階段界線**:官方 Graph API 拿不到第三方粉專內容(2018 後鎖死);爬 FB/IG 貼文違反
Meta ToS。所以**先不爬,優先做下列合規來源**。

**未來可能(使用者傾向):本機帶自己登入資訊爬 FB** — 記錄此方向,但附風險與前提:
- ⚠️ **帳號停權風險(最重要)**:Meta 對登入帳號的自動化偵測很兇,封的是**真人主帳號**。
  → **絕不要用個人主帳號**;用不在乎的獨立帳號,且獨立帳號也常被快速停權。
- ⚠️ **法律/ToS**:登入後爬 = 帶授權繞過存取控制,法律上比爬公開頁更重;Meta 有訴訟前例。
- ⚠️ **技術脆弱**:checkpoint、裝置指紋、限流;維護成本高、隨時會斷。
- **前提條件(真要做時)**:低頻率、只碰自己追蹤的公開粉專、headful、當 best-effort;
  和爬蟲同樣留在本機/住宅 IP。
- **合規優先原則**:先把下面三項(Google 商家貼文 + 粉專連結 + 群眾回報)做完,
  再評估實際還缺多少——很可能缺口比預期小,不值得為它冒帳號風險。

**優先做的合規來源**:
- ✅ **Google 商家貼文**(見「店家動態小泡泡」):店家常把公休/營業公告同步 po 到 Google,
  我們合規就拿得到,涵蓋大部分「粉專營業資訊」的需求。
- ✅ **記錄粉專 URL(只存連結、連出去,不抓內容)**:
  - 自動撿:採集時若 `website` 是 `facebook.com`/`instagram.com`,存成 `fan_page` 欄位;
    Google place 有時也帶社群連結。
  - 詳情面板顯示「FB / IG」按鈕,使用者點過去看最新公告。
- ✅ **公休/臨時異動 → 群眾回報覆蓋(接 P4)**:使用者看到粉專公告「今日公休」,在 app
  回報,蓋掉 Google 的營業時間。這是「粉專營業資訊」進到 app 的實際、可持續、合規路徑。

**最小步**:採集端偵測 website 是否為 FB/IG,存 `fan_page`;詳情面板加連結按鈕。

### 店家動態小泡泡(擷取有趣貼文顯示在店家旁)

需求:店家 po 了有趣的貼文,擷取一小段顯示在地圖店家旁的小對話泡泡。

**好消息:資料合規且已在爬。** 不是 FB/IG,而是 **Google 商家自己發的「最新動態/貼文」**,
就在完整版回應的 `p[122]` 裡(2026-09 實測神山有兩則):
- 活動貼文:「麵王総選挙…7/20–8/16 每日限量20碗《蔥塩冷沾麵》」
- **營業調整公告**:「【營業時間調整公告】因店內設備維護,7月2日延後至17:00營業…」

→ 這順帶補上前面「粉專營業資訊」的缺口:**很多店會把公休/營業公告同步 po 到 Google**,
   我們合規就拿得到。

**做法**:
- 採集端:parser 新增 `posts` 欄位,抽 `p[122]` 的商家貼文(文字 + 日期);存 D1。
- 泡泡內容來源優先序:**最新商家貼文 → 退而取一句精彩評論**(評論已有)。
- 前端:地圖 marker 旁 / 卡片上顯示擷取一小段(截斷 + 「更多」),點開看全文。
  可只對「有近期貼文」的店顯示泡泡,避免雜訊。

**限制**:商家貼文只在完整版(Playwright)回應才有,且非每家店都會發文。

### 價格區間(顯示 + 篩選)

**已在爬**:`price_text`(Google 粗略價格帶,如 `$200–400`)已是採集欄位、詳情面板已顯示。
- 前端加價格篩選 chip(依 Google 帶:$100–200 / $200–400 / $400–600…)。
- 卡片/泡泡也可顯示價格帶。
- **限制**:只在完整版(Playwright)回應才有;級距粗、變異低(實測 30 家全是 $200–400,
  多數拉麵落同一帶)。覆蓋隨 Playwright 成長。

### 菜單照片(擷取 Google 的菜單相片)

**已在爬**(2026-09 實測):Google 有「菜單」相片分類,`p[105]`/`p[171]` 掛著菜單照 URL
(googleusercontent,可放大解析度)。有菜單分類的店抽得到菜單照。
- 採集端:parser 新增 `menu_photos` 欄位,抽「菜單」分類的照片 URL。
- 前端:詳情面板加「菜單」區塊顯示菜單照(可放大檢視)。
- **限制**:完整版(Playwright)才有;非每家店都有菜單分類(店家/使用者要有上傳)。
